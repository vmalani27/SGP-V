# Lab 9: Building an Application Image

## What You're Doing and Why

Every lesson in Module 2 has built toward this capstone milestone: taking a real application codebase and engineering a production-ready container image.

In this lab, you step into the role of a DevOps engineer containerizing a Python service (`~/hello-app`). Rather than following mechanical line-by-line instructions, you will evaluate operational requirements, protect the build context with `.dockerignore`, structure the Dockerfile to maximize build cache efficiency, deploy the container with external port routing, and verify running service health.

## Scenario

An engineering team has handed off a lightweight HTTP service located in `~/hello-app`. The service listens on port `8000`, logs `ready` on startup, and serves HTTP 200 responses.

However, the repository contains dirty local artifacts (`__pycache__`), has no containerization assets, and must be deployed such that operators can reach it on port 8000 while ensuring future code edits rebuild in milliseconds.

## Objectives

1. Audit `~/hello-app` and configure `.dockerignore` to keep cache files and VCS directories out of the build context.
2. Author a `Dockerfile` implementing production standards: official runtime base, isolated working directory, dependency-first caching order, and documented port.
3. Build and tag `hello-app:1.0`, then simulate a source code change and build `hello-app:1.1` to verify layer cache reuse.
4. Deploy the service as a named background container (`hello-service`) with host port forwarding.
5. Verify application health using container logs and host HTTP requests.

## Command Reference

### `docker build -t <name>:<tag> <context-dir>`
Builds an image from the Dockerfile in `<context-dir>` using the specified tag.

### `docker run -d --name <name> -p <host-port>:<container-port> <image>`
Runs a container in detached mode, assigns a readable name, and forwards host traffic to the container port.

### `docker logs <name>`
Prints the standard output and error streams generated by the container process.

### `curl -i http://localhost:<port>/`
Sends an HTTP GET request to the published port and outputs HTTP headers and response body.

## Tasks

- [ ] **context-hygiene** — Protect the build context by creating `.dockerignore` to exclude `__pycache__` and `.git`.
- [ ] **engineer-dockerfile** — Author the Dockerfile based on operational requirements (Alpine base, WORKDIR, dependency-first caching, EXPOSE 8000, CMD).
- [ ] **build-and-verify-cache** — Build `hello-app:1.0`, edit `app.py`, and build `hello-app:1.1` to confirm cache reuse.
- [ ] **run-and-route** — Deploy `hello-service` in the background with `-p 8000:8000`.
- [ ] **verify-service** — Confirm startup logs show `ready` and `curl` returns HTTP 200.

## Reflection

You engineered an end-to-end container deployment by applying the cumulative lessons of Chapters 5–9:
- **Build Context Boundary (Ch 7):** Keeping local cache residue out of the daemon preserves security and speeds up builds.
- **Layer Caching (Ch 8):** Freezing dependencies into a lower layer means routine application code updates build instantly.
- **Port Mapping (Ch 6 & 9):** `EXPOSE` documents where the application listens, but runtime `-p` flag binding is what allows outside traffic into the container.
